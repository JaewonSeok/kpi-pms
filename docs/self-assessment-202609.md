## 1. 이번 진단의 논지

1회차는 저장소의 파일·문서·워크플로를 **열람**해서 판정했다. 2회차는 같은 항목을 **실측**으로 다시 봤다 — 운영 DB를 조회하고, CI를 실제로 돌리고, AI 도구 설정 파일을 열고, 테스트가 정말 실행되는지 확인했다.

그 결과 **1회차가 검출할 수 없었던 결함 11건**이 나왔다. 이 중 상당수는 1회차가 "준수" 또는 "부분준수"로 평가한 항목의 근거를 직접 무너뜨린다.

> **파일이 존재한다는 것과 그것이 동작한다는 것은 다르다.**
> 1회차는 전자만 볼 수 있었다.

## 3. 2회차 신규 발견 (1회차 미검출)

### 3-1. 운영 DB 자격증명이 AI 도구 설정에 평문 — **최고 위험**

`~/.claude/settings.json`의 `permissions.allow` 배열에 프로덕션 Supabase 접속 문자열이 **13회 반복**해 평문으로 있었다. 호스트·사용자·DB명까지 한 줄에 들어 있어 그 문자열 하나로 전 직원 평가 데이터에 접근 가능한 상태였다.

- **원인**: 명령에 비밀번호를 인라인으로 넣고 승인하면 `allow` 목록에 전문이 영구 누적된다
- **조치**: 비밀번호 로테이션, Vercel·로컬 환경변수 교체, 평문 13줄 삭제, 백업 파일 삭제
- ★ **이 파일은 저장소 밖이라 어떤 시크릿 스캔도 닿지 않는다.** #287로 도입한 gitleaks도 검출 범위 밖이다

> **1회차 §4.3 "시크릿 관리 — 부분준수" 판정의 근거는 `.gitignore`에 `.env*`가
> 있다는 것이었다. 실제 최대 노출면은 저장소 밖에 있었다.**

### 3-2. 인증 이벤트가 감사 로그에 6개월간 0건

`audit_logs`의 92종 액션이 전부 업무 행위이고, 로그인·로그아웃 기록이 단 한 건도 없었다(2026-03-17 이후). 누가 언제 접속했는지 조회할 수 없는 상태였다.

- 스키마에는 `ipAddress`·`userAgent` 컬럼이 있으나 인증 경로에서 채워지지 않았다 — 설계는 돼 있고 사용되지 않았다
- Google 로그인 성공/거부는 `authTrace`(콘솔)로만 남아 Vercel 로그에 흔적이 있으나 **쿼리 불가능한 형태**다. credentials 경로는 그조차 없었다
- **조치**: `events` 블록 신설, `AUTH_SIGNIN_SUCCEEDED` / `AUTH_SIGNIN_FAILED` / `AUTH_SIGNOUT` (#300)

### 3-3. 대행 중 업무 액션이 무고한 직원 이름으로 기록 — **감사 무결성**

대행 로그인(master login) 중 수행한 업무 액션의 `audit_logs.userId`가 **대행 대상 직원**의 ID로 기록되고 있었다. 대행 시작 시 토큰이 대상의 claims로 덮어써지기 때문이다.

인사평가 시스템에서 "누가 이 평가를 변경했는가"의 답이 틀린 상태였다. 누락이 아니라 **오기**다.

- 2026-04-14 이후 118 대행 세션이 이 상태로 기록됐다
- **조치**: `actorUserId` 컬럼 추가(#301), 133개 콜사이트 적용(#302), 서버 모듈 7곳(#303)
- ★ **과거 데이터는 복구 불가능하다.** 세션 창(actorId·targetId·시각)으로 추정 리포트는 만들 수 있으나, 추론값을 감사 로그에 쓰는 것은 감사 로그가 아니게 되므로 별도 읽기 전용 리포트로만 다룬다

### 3-4. 대행 만료 감사가 세션 1건당 최대 13행 중복

`MASTER_LOGIN_EXPIRED`가 만료 1회에 9~13행 기록됐다. 4월 0.56배에서 9월 6.45배로 **점진 악화**했다.

- jwt 콜백이 `getServerSession` 호출마다 실행되는데(139개 파일 179회), 토큰 변경이 쿠키로 반영되지 않아 같은 만료가 반복 감지된다
- 앱이 커질수록 페이지당 호출 수가 늘어 증폭이 커지는 구조였다
- ★ **실질 피해는 관측성이다.** 감사 로그가 자기 소음으로 자기를 가렸다 — 100행 조회 시 72%가 중복이라 정작 봐야 할 이벤트가 밀려났다
- **조치**: DB 전이(compare-and-swap)가 실제로 일어났을 때만 기록 (#300)

### 3-5. AI 자동 커밋 훅이 승인 게이트를 무력화

`~/.claude/settings.json`의 전역 `PostToolUse` 훅이 AI가 파일을 편집할 때마다 `git add -A && git commit`을 실행하고 있었다.

kpi-pms의 실질적 승인 통제는 "AI가 작업 후 STOP → 사람이 diff 검토 → 승인 후 커밋"이다. 이 훅은 그 아래를 뚫었다. **AI가 사람 승인 없이 커밋하는 구조**는 §2.3 게이트③ 위반이며 `AI_SAFETY_GUARDRAILS.md`의 explicit approval 원칙과 정면으로 충돌한다.

- 전역 설정이라 kpi-pms 외 모든 저장소에 적용되고 있었다
- `git add -A`라 `.gitignore`에 없는 모든 파일이 대상이었다
- **조치**: 훅 제거

### 3-6. 저장소에 직원 PII 하드코딩

#287로 도입한 pii job이 첫 실행에서 `scripts/` 이메일 리터럴 7건을 탐지했다. 조사 결과 6건이 실제 직원 정보, 1건은 오탐이었다. 한글 실명 1건도 함께 발견됐다.

- **조치**: 관리자 부트스트랩 스크립트 2개 삭제, Usage 예시 문자열 교체 (#298)
- ★ 남은 것: `tests/` 103 occurrence / distinct 로컬파트 51개 중 합성 표지 없는 것 43개. `docs/` 2건. 미판정
- ★ pii 룰은 `src/`·`scripts/`만 보고 이메일 정규식만 쓴다. **한글 실명은 영원히 검출되지 않는다**

> **1회차 §4.5 "AI 특화 보안 — 준수" 는 46개 항목 중 단 2건의 준수 중 하나였다.
> AI 프롬프트 경로는 실제로 막혀 있었으나, 같은 PII가 저장소 안에 박혀 있었다.**

### 3-7. 테스트 168개 중 87개(52%)가 CI에서 실행되지 않음

`package.json`의 `test` 체인에 등록되지 않은 테스트 파일이 87개였다. 파일은 존재하지만 CI가 한 번도 돌린 적이 없다.

- 87개 중 실행 가능한 64개를 등록하고, FAIL 23개는 부채 목록으로 관리 (#305)
- FAIL 23개는 전부 런타임 assertion 실패다 — **한때 통과했던 테스트가 지금은 실패한다**는 뜻이며, 코드가 기대에서 이탈한 것인지 테스트가 낡은 것인지 미판정
- 등록 누락을 CI가 검출하도록 `scripts/check-test-chain-coverage.ts` 신설

**실제 피해가 있었다.** #302가 도입한 `Session` 교차 타입 회귀를 `evaluation-2026-readiness-population.test.ts`가 잡을 수 있었다. 28/28 PASS였다가 파일 전체 컴파일 불가가 됐는데, 체인 미등록이라 CI가 통과시켰고 **이틀 뒤에야 우연히 발견**돼 #304로 수정했다.

> **1회차 §4.4 "테스트 파일 170개 … 볼륨 자체는 상당히 두터움" 이 부분준수 판정의
> 근거였다. 실제로 CI가 실행한 것은 81개였다.**

### 3-8. 테스트가 동작이 아니라 텍스트를 검사한다

`org-kpi-team-ai-workspace.test.ts`는 `serverSource.includes('generateTeamKpiRecommendationSet')`처럼 **소스 파일에 문자열이 있는지만** 확인한다. 함수를 호출하지 않는다.

실측: #303의 감사 귀속 코드를 통째로 제거해도 7/7 PASS였다.

- 이번에 확인한 3개 중 3개가 이 방식이었다
- 168개 중 이런 테스트의 비중은 **미측정**
- ★ 이 비중이 §4.4 판정의 실질을 좌우한다. 3-7이 "몇 개가 도는가"라면 이것은 "도는 것이 무엇을 검증하는가"다

### 3-9. 스키마 드리프트 — 마이그레이션 2개월 반 미기록

`prisma migrate status` 확인 결과 `20260630_add_org_kpi_exception_request`가 미적용 상태였다. 그런데 해당 테이블은 운영 DB에 **이미 존재**했고 컬럼·인덱스·FK가 마이그레이션 SQL과 완전히 일치했다.

6월 30일에 DDL이 직접 실행되고 `_prisma_migrations` 기록만 빠진 것이다. **2개월 반 동안 아무도 몰랐다** — 배포 전 `migrate status`를 확인하는 절차가 없었다.

- **조치**: `migrate resolve --applied`로 이력 정합화 (2026-09-17 조치 완료 — migrate resolve --applied)
- 이것이 §2.3 게이트②(DB 스키마 변경 승인·ADR 기록) 미준수의 실증이다

### 3-10. 로컬 `.env`가 운영 DB를 가리킴

로컬 개발 환경의 `DATABASE_URL`이 프로덕션 Supabase를 가리키고 있었다. `docker-compose`와 `localhost:5433`이 있으므로 로컬 DB는 존재하나 사용되지 않는다.

- `prisma migrate dev` / `db push` / `migrate reset`을 로컬에서 실행하면 **운영 DB에 적용된다.** `migrate reset`은 전체 삭제다
- 실제로 마이그레이션 생성 시 `migrate dev --create-only`조차 섀도우 DB에 연결을 시도하므로, 연결이 없는 `migrate diff`로 우회해야 했다
- 테스트 실행도 마찬가지다. 격리하지 않으면 운영 DB에 붙는다
- **부분 완화** — #315 로 `db:migrate`/`db:reset`/`db:push`/
  `db:studio`/`db:seed` 에 로컬 DB 가드를 걸었다. `.env` 자체는
  미변경이며 `npx prisma` 직접 실행은 우회된다

### 3-11. 타입 검사가 꺼진 파일

`src/server/org-kpi-team-ai.ts` 최상단에 `// @ts-nocheck`가 있다. 이 파일은 `tsc --noEmit`의 검사 대상이 아니다.

#303에서 이 파일에 타입을 추가했으나 **컴파일 타임 방어 효과가 없다.** 3-8과 겹쳐 이 파일은 컴파일·런타임·CI 세 겹이 모두 비어 있는 상태였다.

## 4. 방법에 대한 관찰

신규 발견 11건 중 **파일 열람으로 검출 가능한 것은 3-11(한 줄 주석) 하나뿐**이다. 나머지 10건은 다음 중 하나가 필요했다:

| 검출 수단 | 발견 |
|---|---|
| 운영 DB 조회 | 3-2, 3-3, 3-4, 3-9 |
| 저장소 밖 설정 파일 점검 | 3-1, 3-5, 3-10 |
| CI 실제 실행 | 3-6 |
| 체인 등록 여부 대조 | 3-7 |
| 코드를 고의로 깨뜨려보기(음성 대조) | 3-8 |

마지막 항목이 특히 그렇다. 테스트가 통과한다는 사실만으로는 그 테스트가 무언가를 검증하는지 알 수 없다. **수정 전 코드에서 실패하는지 확인**해야 한다. 이번 진단에서 이 방법으로 두 건의 무검증 상태를 확인했다(#303, 3-8).
