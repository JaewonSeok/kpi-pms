# 결함 심각도 체계

| 항목 | 값 |
|---|---|
| 표준 근거 | AI Native QA 운영 가이드 §4, §6 (Redmine 운영정책 연계) |
| 작성일 | 2026-09-17 |
| 해소 대상 | 1회차 자가 진단 §4.4 "정량 결함 추적·심각도 분류 체계 없음" |

---

## 1. 배경

kpi-pms에는 심각도·우선순위 표기가 **4갈래로 파편화**돼 있었고 서로 매핑이 없었다.

| 위치 | 표기 | 의미 |
|---|---|---|
| `docs/operations/incident-runbook.md` | Sev1~3 | 운영 장애 등급 |
| `docs/operations/data-migration-and-launch-plan.md` | P1~P4 | 런칭 하이퍼케어 이슈 분류 (SLA 포함) |
| `docs/operations/current-handoff.md` | P0~P2 | 작업 우선순위 |
| `docs/product/global-benchmark-gap-analysis.md` | P0~P2 | 제품 로드맵 우선순위 |

같은 `P` 표기가 세 가지 다른 의미로 쓰이고, 결함 심각도 자체는 표준 4등급으로
분류된 적이 없었다.

---

## 2. 정본 — 두 체계는 통합하지 않는다

**결함(defect)과 장애(incident)는 판정 축이 다르다.** 통합하지 않고 각각 유지한다.

| | 체계 | 판정 축 | 출처 |
|---|---|---|---|
| **결함** | Critical / Major / Normal / Minor | 기능 영향도 | AI Native QA 운영 가이드 §4 |
| **장애** | Sev1 / Sev2 / Sev3 | 영향 범위·긴급도 | 전사 장애대응지침 |

둘 다 전사 표준이며 kpi-pms가 임의로 합칠 수 없다. 하나의 사건이 양쪽 등급을
동시에 가질 수 있다 — 운영 중 발생한 Critical 결함은 Sev1 장애이기도 하다.

---

## 2-1. 나머지 세 축

보안 검사 가이드 §1 은 별도의 판정 등급을 정의한다.
**적합 / 부적합 / 해당없음** 3단계이며, 이것은 검사 항목이 기준을
충족하는지에 대한 판정이지 결함의 심각도가 아니다.

| 축 | 등급 | 판정 기준 | 출처 |
|---|---|---|---|
| 결함 심각도 | Critical / Major / Normal / Minor | 기능 영향도 | AI Native QA 운영 가이드 §4 |
| 장애 등급 | Sev1 / Sev2 / Sev3 | 영향 범위·긴급도 | 전사 장애대응지침 |
| 검사 판정 | 적합 / 부적합 / 해당없음 | 기준 충족 여부 | 보안 검사 가이드 §1 |
| 코드 변경 위험도 | Critical / High / Medium / Low | 변경의 위험도 | SDLC Requirements §4.3 |

### ★ Critical 이 두 축에 나타난다

**결함 심각도의 Critical** 은 "기능 사용 불가(Crash)" 를 뜻하고,
**코드 변경 위험도의 Critical** 은 게이트③ 에서 "AI Code Reviewer 가
자동 거절" 하는 등급이다. 같은 단어이나 대상과 의미가 다르다.

| 위험도 | 게이트③ 처리 (§4.3) |
|---|---|
| Critical | 자동 거절 |
| High | 필수 검토 |
| Medium / Low | 자동 통과 |

★ kpi-pms 에는 이 1차 자동 판정이 **미구현**이다. PR 은 사람이 전량
검토한다. [게이트 SLA](./gate-sla.md) 5절 참조.

### 검사 판정 규칙 (보안 검사 가이드 §1)

- **근거 없이 '적합' 판정 금지.** 설정 캡처·API 응답·스캔 리포트·
  코드 인용 중 하나가 반드시 있어야 한다
- **부적합** 항목에는 개선요청(담당·기한)을 명시한다
- 쓰지 않는 기능은 **'해당없음' + 사유**로 표기한다
- 확인 불가 항목은 추측하지 말고 담당자 질문으로 이관한다

★ 검사 판정과 결함 등급은 동시에 존재한다. 부적합 판정에서 드러난
결함에는 별도로 4등급을 부여한다. 예를 들어 "시크릿 관리 — 부적합"
판정의 원인이 된 '운영 자격증명 평문 노출' 은 Critical 결함이다.

## 3. 결함 심각도 4등급 (표준 §4)

| 등급 | 정의 | kpi-pms 판정 예시 |
|---|---|---|
| **Critical** | 기능 사용 불가(Crash), 기본기능 미구현·미동작, 기획 기능 전무 동작 | 인증 이벤트가 감사 로그에 6개월간 0건 — 접근기록이라는 요구 기능이 미구현 (#300) |
| **Major** | 기본기능 오동작, 기획과 상이한 동작, 미완료, Main UI 오동작 | 대행 중 업무 액션이 대행 대상 ID로 기록 — 감사가 기획과 다르게 동작 (#302) |
| **Normal** | 완결성 부족(UI), 기획 오류, 결함 빈도 낮음, 일부 미수행(대체 가능) | `MASTER_LOGIN_EXPIRED` 중복 기록 — 기록 자체는 남으나 완결성 부족 (#300) |
| **Minor** | 사용성 개선 제안, 신규 기능 요구 | CI 요약에서 0건일 때 빈 블록이 렌더링되는 문제 |

### 판정 원칙

- **Critical은 면제 불가**다(품질 검증 가이드 §101). 알파·베타·실서비스 어느
  게이트에서도 미해결 Critical이 있으면 승격하지 않는다
- **Critical·Major는 전건 해결**이 정량 기준이다(§4). Normal·Minor는 이관 가능
- 등급은 **기능 영향도**로 판정한다. 발견 시점·수정 난이도·긴급도는 판정 근거가
  아니다

### ★ 이 체계로 분류되지 않는 것

표준 4등급은 **제품 기능** 기준이다. 개발 인프라 결함(CI·테스트·타입 검사)을
분류할 칸이 없다.

예: #302가 도입한 `Session` 타입 회귀는 테스트 컴파일을 깨뜨렸지만 제품 기능에는
영향이 없었다. 4등급 어디에도 정확히 맞지 않는다.

**운용 규칙**: 제품 기능 영향이 없는 개발 인프라 결함은 4등급을 부여하지 않고
`infra` 라벨로 분리 추적한다. 다만 **그 결함이 다른 결함의 검출을 막는 경우**
(예: 테스트가 CI 체인 밖이라 회귀를 놓친 경우)는 Major로 판정한다 — 품질 게이트
자체가 오동작한 것이기 때문이다.

## 4. 장애 등급 (Sev, 참고)

`incident-runbook.md`의 정의를 유지한다.

| 등급 | 정의 |
|---|---|
| Sev1 | 로그인 불가, DB 사용 불가, 대규모 데이터 손상, 전면 5xx |
| Sev2 | AI assist 불가, 알림 파이프라인 정지, 관리자 워크플로 차단 |
| Sev3 | 단일 기능 저하, 경미한 UI 이슈, 비차단 연동 실패 |

### 결함 등급과의 관계

Sev는 **운영 중 발생한 사건**의 등급이고, 결함 등급은 **그 사건의 원인이 된
결함**의 등급이다. 통상 다음과 같이 대응하나 **일대일이 아니다**.

| 장애 | 통상 원인 결함 | 예외 |
|---|---|---|
| Sev1 | Critical | 외부 서비스 장애 등 결함이 아닌 원인 |
| Sev2 | Critical ~ Major | 설정 오류 등 |
| Sev3 | Normal ~ Minor | Critical 결함이 경미한 경로에서만 드러날 수 있음 |

★ 장애 대응 중에는 Sev로 판단하고, 사후 결함 등록 시 별도로 4등급을 부여한다.
두 등급이 달라도 정상이다.

## 5. 파편화 정리

### 5-1. P1~P4 (하이퍼케어) → 4등급으로 흡수

`data-migration-and-launch-plan.md`의 P1~P4는 결함 분류이므로 4등급으로 대체한다.
단 **SLA는 유지 가치가 있다.** 표준 4등급에는 대응 시간 규정이 없다.

| 기존 | 대체 | SLA (kpi-pms 자체 기준, 유지) |
|---|---|---|
| P1 | Critical | 즉시 착수, 30분마다 진행 갱신 |
| P2 | Major | 30분 내 확인 |
| P3 | Normal | 당일 내 |
| P4 | Minor | 백로그 |

★ 이 SLA는 런칭 하이퍼케어 기간의 기준이다. 평시에는 게이트 승격 조건
(Critical·Major 전건 해결)이 적용된다.

### 5-2. P0~P2 (작업·로드맵 우선순위) → 이름 변경

결함 체계가 아니므로 `P` 표기를 쓰지 않는다. 혼동만 만든다.

| 위치 | 기존 | 변경 |
|---|---|---|
| `current-handoff.md` | P0/P1/P2 | `순위 1/2/3` |
| `global-benchmark-gap-analysis.md` | P0/P1/P2 | `로드맵 1/2/3` |

### 5-3. 코드의 `severity` — 범위 밖

`src/` 하위에 6종의 `severity` 값(UI 배지, 검증 결과, 운영 메트릭)이 있으나
**결함 추적이 아니다.** 같은 단어를 쓸 뿐 도메인이 다르므로 통합하지 않는다.

## 6. 결함 Workflow (표준 §6)

★ **개발 일감 Workflow와 다른 체계다.** 혼동하지 않는다.

| | 단계 |
|---|---|
| **결함** | 등록(QA) → 분석 → 수정 → 해결 → 확인(QA) → 종료 (6단계) |
| **개발 일감** | 등록 → 검토 → 진행 → 완료 → 종료 (5단계) |

### 주요 규칙

- **담당자 유지 원칙**: 개발자는 수정 후 담당자를 QA로 바꾸지 않고 상태만
  '해결'로 변경한다
- **Reopen 기준**: 동일 현상 재현 또는 담당자 변경 시 Reopen. **수정과 무관한
  결함은 Reopen이 아니라 신규 등록**한다. QA 검증 종료 직전 Reopen 리뷰
  프로세스를 필수 수행
- **이관**: 일정 내 대응 불가 결함은 사유 작성 후 PM 검토 + QA 검토를 거쳐
  Backlog·차기 버전으로 이관
- **Known Issue**: 대응 자체가 불가한 결함은 사유 작성 후 PM 검토 + QA 검토를
  거쳐 Known Issue로 등록·종료

## 7. kpi-pms 적용 — 구조적 제약

표준은 **QA 조직**이 결함을 등록하고 확인하는 것을 전제한다. kpi-pms에는 별도 QA
조직이 없으므로 등록·수정·확인을 동일인이 수행한다.

이는 [예외승인 요청서](./exception-request-20260914.md) A-3(작성자≠승인자 분리)·
A-4(AT 주관)와 같은 구조적 제약이며, 이 문서로 해소되지 않는다.

### 대체 운용

- 결함은 **GitHub Issue**에 등록하고 등급을 라벨로 부여한다
  (`sev:critical` / `sev:major` / `sev:normal` / `sev:minor` / `infra`)
- Reopen은 GitHub Issue 재오픈으로 추적한다
- **확인(5단계)은 수정과 다른 세션에서 수행한다.** 동일인이라도 시점과 컨텍스트를
  분리해 자기 수정을 즉시 확인하지 않는다
- Critical·Major는 **회귀 테스트 동반을 필수**로 한다. 수정 전 코드에서 실패하는지
  확인(음성 대조)한 뒤 통과시킨다

★ 마지막 항목은 표준 §4의 "테스트 유효성 검사 — 수치 충족만을 위한 무의미한
테스트를 막기 위해 실질 검증을 하는지 확인" 조항에 대한 kpi-pms의 이행 방식이다.

## 8. 미결

- **라벨 생성**: GitHub Issue 라벨 5종이 아직 만들어지지 않았다
- **기존 문서 반영**: 5-2의 이름 변경이 아직 적용되지 않았다
- **QA Pass rate 97.5%**: 측정 체계가 없다. 분모(실행 테스트 수)는 확보됐으나
  (144개) 결함 대비 통과율을 산출하는 방식이 정의되지 않았다
- **소급 분류**: 2회차 자가 진단에서 발견한 11건에 등급을 부여하지 않았다.
  3절 예시 3건만 판정돼 있다
- **세 축의 상호 참조 규칙**: 검사 부적합이 어떤 조건에서 Critical
  결함이 되는지 판정 기준이 정의되지 않았다
- **코드 변경 위험도 판정 기준**: 게이트③ AI 1차 자동 판정이
  미구현이므로 Critical/High/Medium/Low 를 나누는 기준이 없다
