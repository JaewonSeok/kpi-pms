# 승인 게이트 — 판정 기한과 대행자

| 항목 | 값 |
|---|---|
| 표준 근거 | AI Native SDLC Requirements §2.3, Squad 개발 운영 가이드 2-1 |
| 수립일 | 2026-09-18 |
| 해소 대상 | 1회차 자가 진단 §2.3 "각 게이트의 SLA·대행자 지정 없음" |

---

## 1. 표준이 요구하는 것

> 각 게이트에는 **판정 기한(SLA)과 대행자를 지정한다(필수)**.

Squad 개발 운영 가이드 2-1 이 기본값을 정하며, 프로젝트별 조정이 가능하다.

| 게이트 | 기본값 |
|---|---|
| ① 설계 확정 / ② DB 스키마 변경 / ③ MR 병합 | 1영업일 이내 |
| ④ 베타 배포 / ⑤ 실서비스 배포 | 3영업일 이내 |

- **대행자 사전 지정**: 승인 주체 조직의 장이 게이트별 대행자를 미리 지정
- **에스컬레이션**: 승인자 부재 또는 기한 초과 시 대행자에게 넘긴다
- 대행 승인도 정규 승인과 동일하게 증적을 남긴다
- 프로젝트 착수 시 지정·기록 여부는 **자가 진단 B1 항목**으로 점검한다

★ 1회차 자가 진단은 이 B1 항목을 확인하지 않았다. 표준 자체가 점검하도록
정한 항목을 진단이 누락한 사례다.

## 2. kpi-pms 게이트별 지정

| # | 게이트 | 표준 승인 주체 | kpi-pms 승인자 | SLA | 대행자 |
|---|---|---|---|---|---|
| ① | 설계 확정 | 연구개발본부 개발담당자 | 재원 | 1영업일 | **없음** |
| ② | DB 스키마 변경 | 연구개발본부 개발담당자 | 재원 | 1영업일 | **없음** |
| ③ | MR 병합 | 저장소 관리자 | 재원 | 1영업일 | **없음** |
| ④ | 베타 배포 | 품질경영본부 | **조직 부재** | — | **없음** |
| ⑤ | 실서비스 배포 | PM 승인 + CTO 최종 승인 | **조직 부재** | — | **없음** |

①②③ 은 기본값을 그대로 채택한다. ④⑤ 는 승인 주체 조직이 없어
[예외승인 요청서](./exception-request-20260914.md) A-1·A-2 로 제출했으며
회신 대기 중이다.

### 작성자 ≠ 승인자

표준은 이를 **권고**로 규정한다(필수 아님).

> 작성자와 승인자는 **가급적** 분리한다(**권고**) — 본인이 작성 주체
> (AI에게 지시한 경우 포함)인 산출물은 가급적 본인이 승인하지 않는다.

★ 예외승인 요청서 A-3 은 이 항목을 필수 조항처럼 예외 신청했다. **과잉
신청이며 회신 시 정정한다.** 권고 항목이므로 미분리 자체는 미준수가 아니다.

## 3. ★ 대행자 부재 — 형식 문제가 아니다

5개 게이트 전부 대행자를 지정할 수 없다. 승인자가 1명이므로 대행할 사람이
존재하지 않는다.

이는 서류상 미준수가 아니라 **실제 운영 위험**이다.

### 재원 부재 시 발생하는 것

| # | 영향 |
|---|---|
| 1 | 5개 게이트 전부 정지. MR 병합·스키마 변경·배포 승인 불가 |
| 2 | `AI_SAFETY_GUARDRAILS.md` 가 AI 의 프로덕션 `migrate deploy` 를 금지하므로 **스키마 변경이 구조적으로 불가능** |
| 3 | 운영 DB 자격증명이 재원 로컬 환경에만 존재. 2026-09-17 로테이션 후 새 값을 아는 사람이 없다 |
| 4 | break-glass 관리자 계정(`ADMIN_PASSWORD`)도 동일 |
| 5 | 장애 발생 시 Vercel 롤백·Supabase 접근을 수행할 사람이 없다 |

**버스 팩터 1.** 인사평가 시스템이며 평가 시즌에 정지하면 전사 일정에 영향이
간다.

### 완화책

**없다.** 이 문서는 완화책을 지어내지 않는다.

가능한 방향은 있으나 실행 의사가 확인되지 않은 것을 문서에 적으면, 대책이
있는 것처럼 보이면서 실제로는 없는 상태가 된다 — `bcryptjs` 가 설치만 되고
미사용이던 것과 같은 패턴이다.

★ 다음 방향은 **검토 대상이며 결정된 사항이 아니다.**

- 인사팀 내 1명에게 Vercel·Supabase 읽기 권한 부여 (장애 확인만 가능)
- 자격증명을 사내 비밀번호 관리 도구에 보관
- 게이트③ 한정으로 대행 승인자 지정

**판단 필요.** 조직 차원의 결정이며 이 문서의 범위를 넘는다.

## 4. 게이트⑤ 최종 검증 3문

표준 §5.1 은 게이트⑤ 승인 전 승인자가 다음 세 질문에 **근거를 들어** 답할
수 있어야 한다고 규정한다(필수).

| # | 질문 | 근거 출처 | kpi-pms 현황 |
|---|---|---|---|
| ① | 왜 이 기능·코드가 존재해야 하는가 | 요구사항 추적 (§4.1) | PRD·ADR 로 일부 가능 |
| ② | 왜 프로덕션에 넣어도 충분히 안전한가 | **3대 감사 결과** | ★ **답할 수 없음** |
| ③ | 틀렸을 때 무엇을 할 것인가 | 롤백·Runbook | `incident-runbook.md` + 마이그레이션 롤백 절차(#301) |

### ★ ② 에 답할 수 없다

3대 감사 중 **보안만 1차 검사가 있고 품질·인프라는 미수행**이다.
[감사 증적](../audit/README.md) 참조.

표준은 *"이 결과들의 확인 없이 게이트⑤를 승인할 수 없다"* 고 명시한다.
따라서 현재 kpi-pms 는 **게이트⑤ 를 정식으로 통과할 수 없는 상태**이며,
운영 배포는 이 게이트를 거치지 않고 이루어지고 있다.

이는 예외승인 A-2 의 사유이자 그 실증이다.

## 5. 게이트③ — AI 1차 판정 미구현

표준 §4.3 은 게이트③ 을 2단계 구조로 규정한다.

> 저장소 기준 문서로 AI Code Reviewer 가 1차 자동 판정
> (위험도 4등급: Critical 자동거절 / High 필수검토 / Medium·Low 자동통과)
> → 저장소 관리자가 핵심 변경만 2차 검토·승인

kpi-pms 에는 **1차 자동 판정이 없다.** PR 은 사람이 전량 검토한다.

★ 1회차 자가 진단이 게이트③ 을 "부분준수" 로 판정한 근거는 "PR 병합 흔적이
있다" 였다. 실제로는 2단계 구조의 1단계가 통째로 없다.

★ 위험도 4등급(Critical/High/Medium/Low)은
[결함 심각도](./defect-severity.md)의 4등급(Critical/Major/Normal/Minor)과
**다른 체계**다. 전자는 코드 변경의 위험도, 후자는 결함의 심각도다.
심각도 체계 문서에 **네 번째 축으로 추가가 필요하다.**

## 6. 승인자 브리핑 — 학습용 설명 자료

표준 §2.3 은 모든 게이트에 공통으로 다음을 요구한다(필수).

> 승인자는 승인 전 AI 가 생성한 **학습용 설명 자료**를 제공받는다.
> 판단은 요약 수용이 아니라 **이해에 근거한다**.

kpi-pms 는 이를 **PR 본문**으로 이행한다. 다만 형식이 정의돼 있지 않다.

### 현행 관행 (2026-09 기준)

- PR 본문에 배경·결정·기각한 대안·검증 결과·남은 과제를 기재
- 보고는 요약이 아니라 **요약 불가능한 원본 출력**(diff, 테스트 출력, SQL
  결과)으로 수령
- 수정 전 코드에서 실패하는지 확인(음성 대조)한 근거를 포함

★ 이 관행은 §2.1 "요약 수용이 아니라 이해에 근거한 판단" 의 취지와 부합하나
**문서화된 형식이 아니다.** PR 템플릿 미수립 상태이며, 게이트③ 미준수 근거와
같은 항목이다.
