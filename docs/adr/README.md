# ADR (Architecture Decision Records)

| 항목 | 값 |
|---|---|
| 표준 근거 | SSOT 운영 가이드 1절 (기본 관리 문서 18종), SDLC Requirements §2.3 §4.1 |
| 수립일 | 2026-09-18 |
| 해소 대상 | 1회차 자가 진단 §2.3 "ADR 파일·디렉터리 검색 결과 0건" |

---

## 1. 무엇을 ADR 로 쓰는가

**결정과 기각한 대안이 함께 있을 때만** ADR 이다.

| | ADR 대상 | ADR 아님 |
|---|---|---|
| 형태 | "A 대신 B 를 택했다" | "현재 구조는 이렇다" |
| 필수 | 기각한 대안과 그 사유 | — |
| 예 | 설계 결정, 스키마 변경, 아키텍처·보안 판단 | 설명 문서, 계획서, 현황 진단 |

★ 기각한 대안이 없으면 ADR 이 아니라 **설계 문서**다. 그것을 ADR 포맷으로
옮기면 "대안과 기각 사유" 절을 지어내야 하고, 그 순간 기록이 아니라 창작이
된다.

### 작성 시점 (§2.3)

- 게이트① 설계 확정
- 게이트② DB 스키마 변경
- 주요 아키텍처·보안 결정

---

## 2. 형식

```
## 상태          Accepted / Superseded / Deprecated
## 맥락          왜 이 결정이 필요했는가
## 결정          무엇을 정했는가
## 대안과 기각 사유   ★ 필수. 이것이 없으면 ADR 이 아니다
## 결과          이 결정으로 무엇이 좋아지고 무엇을 감수하는가
## 레드팀 반론    ★ 0002 부터 적용
```

레드팀 반론 절은 [레드팀 운영 규약](../governance/redteam.md) 2절 형식을
따른다. **기각된 반론도 사유와 함께 기록**한다.

## 4. 기존 문서 검토 결과 (2026-09-18)

ADR 체계 수립 시점에 `docs/` 의 설계 결정 성격 문서 6종을 검토했다.
**1종만 이관했다.**

| 문서 | 판정 | 사유 |
|---|---|---|
| `A1_설계_미리보기_2026등급.md` | **이관 → 0002** | §3.2·§3.5 에 결정과 기각 사유가 함께 기재 |
| `2026-evaluation-official-save-flow-design.md` | 미이관 | 단일 결정만 제시. 기각한 대안 없음 |
| `2026-evaluation-official-schema-boundary-rfc.md` | 미이관 | 동일. 상세하나 대안 비교가 아님 |
| `UIUX_REDESIGN_BLUEPRINT.md` | 미이관 | 설명 문서. "현재는 이렇고 이렇게 바꾼다" |
| `UIUX_SCREEN_REDESIGN_PLAN.md` | 미이관 | 계획서. route 별 현황→계획 나열 |
| `시연_사이클_진단.md` | 미이관 | 현황 진단 + 제품·데모 기획 선택. 코드 설계 결정이 아님 |

★ **미이관 문서는 삭제하지 않는다.** 설계 문서로서의 가치는 그대로이며,
ADR 이 아닐 뿐이다. 각 문서는 원래 위치에 남는다.

★ 미이관 4종을 ADR 로 옮기려면 "대안과 기각 사유" 를 새로 작성해야 한다.
원문에 없는 것을 만드는 일이므로 하지 않는다. 이 판단 자체를 여기 기록해,
다음 진단에서 "RFC 가 ADR 로 이관되지 않았다" 로 재차 잡히지 않게 한다.

## 5. 소급 작성 금지

- 과거 결정을 ADR 로 **새로 만들지 않는다.** 원문에 결정과 기각 사유가
  기록돼 있는 경우에만 이관한다
- 이관 시 원문에 없는 내용을 추가하지 않는다
- 레드팀 반론 절은 규약 수립(2026-09-18) 이후 결정부터 실질적으로 채워진다.
  그 이전 결정의 이관분은 "해당 없음" 으로 표기한다
