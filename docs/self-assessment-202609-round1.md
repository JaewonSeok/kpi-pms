## 1. 핵심 요약

**인간 승인 게이트가 사실상 전무하다.** 표준은 5개 필수 게이트(설계확정 / DB스키마 / MR병합 / 베타배포 / 실서비스배포, §2.3)를 요구하지만, kpi-pms에는 PR 템플릿·CODEOWNERS·브랜치 보호 문서가 전혀 없고(.github/에 ci.yml만 존재), 배포 승인 주체(PM/CTO/QA/보안팀)도 지정돼 있지 않다. `docs/AI_SAFETY_GUARDRAILS.md`의 "명시적 승인 없이는 금지" 규칙이 유일하게 게이트와 유사하지만, 이는 AI 에이전트 자기규율 문서일 뿐 조직적 승인 절차가 아니다.

**버전 체계가 표준과 완전히 다르다.** 표준은 4자리 Major.Minor.Patch.QA(§3.3)를 요구하나, `package.json`은 `"version": "0.1.0"`에 고정돼 있고 `git tag --list`는 빈 결과를 반환한다 — 릴리스가 Git 태그로 식별되지 않는다.

**보안 통제의 다수가 미구현 상태로 문서에 자백돼 있다.** `docs/auth-rbac-matrix.md`가 "Password reset, failed-login lockout, and GWS sync are not yet implemented in code"라고 명시하며, `src/lib/auth.ts:588-590`은 관리자 비밀번호를 `credentials.password === process.env.ADMIN_PASSWORD`로 평문 비교한다(해시·bcrypt 미사용, 소스 전체에서 bcrypt 참조 0건). MFA·CAPTCHA·로그인 실패 잠금 관련 코드도 검색되지 않는다.

**CI 파이프라인에 보안 스캔 단계가 없다.** `.github/workflows/ci.yml`은 lint → typecheck → build → test 4단계뿐이며, 표준이 필수로 요구하는 SAST/SCA(CVE)/시크릿 스캔/PII 검출이 파이프라인 어디에도 없다.

**Redmine·SSOT 상세 문서 체계가 표준과 다른 방식으로 대체 운영된다.** 저장소 전체에서 "Redmine" 문자열이 한 건도 검색되지 않으며, 대신 GitHub Issue/PR과 `docs/operations/current-handoff.md`·`next-chat-prompt.md` 같은 자체 핸드오프 문서로 일감·컨텍스트를 관리한다. ADR·ERD 문서도 별도로 존재하지 않는다.

**PDCA/레드팀/3대 감사는 프로젝트 규모상 사실상 전무하다.** `plan.md`/`result.md`, 레드팀 반론 기록, 품질·보안·인프라 감사 결과 파일 어느 것도 저장소에서 발견되지 않았다 — 다만 이는 본사 Squad 체계를 전제로 한 조항이라, 단일 사내 프로젝트에는 애초에 설계상 무겁게 적용되지 않을 여지가 있다.

## 3. 적용 대상 여부에 대한 소견

표준 자체가 "연구개발본부"라는 전사 조직, Squad 체계, 품질경영본부·정보보안팀·클라우드기술팀이라는 별도 부서의 존재를 전제로 설계돼 있다. kpi-pms는 사실상 1인(또는 극소수) 바이브코딩 프로젝트이므로, 미준수 항목을 **구조적 한계**와 **즉시 개선 가능한 항목**으로 나눠 볼 필요가 있다.

### 구조적으로 적용이 어려운 부분
